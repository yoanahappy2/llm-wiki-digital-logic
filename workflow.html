目標：避免教學簡報只生成好看的版面，卻出現概念錯誤或缺少來源。先建立可追溯的 Wiki，再讓簡報引用 Wiki。

資料處理主流程

核對來源5 個 URL 與章節標題
→
逐篇 Ingestraw → Wiki Markdown
→
查詢 Wiki按 index 搜尋並引用
→
Wiki Lint連結、概念、真值
→
產生 HTML12 頁可互動簡報
迴圈：資料章節與主題不符、概念矛盾、互動測試失敗 → 回到「資料整理／來源檢查」修正；通過後才重新產生 HTML。並非不斷讓 AI 重寫整份簡報。

為什麼把檢查提前？

邏輯閘、半加器和 DFF 有容易混淆的定義：XOR≠OR；Carry = AND；DFF 範例需聲明時鐘觸發型態。如果等到做完簡報才發現錯誤，可能得修改多頁。因此先檢查 Wiki 的事實與來源對應，再產生簡報，最後才檢查 UI 與連結。

反思（依本次試跑）

本次實際出錯節點：「來源核對」和「Wiki HTML 頁面生成」。來源 S05 曾將 MIT 第 9 章誤標成 FSM，第 6 章才是正確來源；第一次視覺檢查發現，檢查提醒欄位顯示了未展開的模板文字，而不是預期的中文核對說明；這是本次實際記錄到的問題，不能據此推論多次執行的錯誤頻率。

把檢查往前移：在「每篇資料 ingest 之前」增加原站標題與章節核對，並在「Wiki 頁面完成、輸出教學簡報之前」新增模板殘留檢查；來源 ID、XOR 真值與半加器公式也在生成前先核對。

Workflow 修改：改為「來源主題核對 → 逐篇 ingest 到 Wiki → Wiki lint／查詢 → 輸出簡報 → 實際操作驗收」。若模板字串未替換，直接停止匯出並回到 Wiki 生成節點修正，不讓錯誤流入最後作品。

三組實際 Wiki 查詢

問題讀取的概念頁回答與來源
XOR 跟 OR 有什麼不同？C01A=B=1 時 OR=1、XOR=0。[S01]
半加器的進位如何算？C02Carry = A AND B、Sum = A XOR B。[S02]
FSM 為什麼需要記住狀態？C05 + C04用有限狀態保存必要的輸入歷史，決定下個狀態。[S05][S04]

三次查詢先讀 wiki/index.md、找到對應 Markdown 概念頁，再根據內容撰寫附來源 ID 的回答。實際檢索及答案在 checks/query_results.json；這裡的離線檢索程式不是聲稱有自動 LLM API 推論。
